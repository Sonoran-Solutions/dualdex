# 2. Primary goal A — close the remaining live operand authority gaps

At minimum investigate:

## A. `GetMoveTargetCount(ctx)`

C4b models the operand but no production reader supplies it.

Implement an authoritative runtime representation if it can be derived safely from existing battle state.

The required semantics are the actual H&S rule:

* spread reduction is based on the number of **currently present targets**;
* `targetCount == 2` → Gen-III spread reduction applies;
* `targetCount == 1` → no spread reduction;
* unknown/unreadable → fail closed.

Do not infer this merely from:

* `gameType == Doubles`;
* the static move target class;
* party size;
* species/HP coincidence.

Prefer authoritative battler-presence / absent-flag / battle-controller state already supported by the runtime reader.

Add negative tests that prove stale, ambiguous, or unavailable state cannot fabricate a count.

## B. Dynamic move type

Determine exactly whether a supported ordinary H&S calculation can have a move type that differs from its static move record because of live battle state.

If yes:

* identify the exact source-of-truth state;
* implement a boundary-owned reader/observation;
* validate its domain;
* consume it in calculation.

If the bounded supported move subset can be proven not to exercise a dynamic move type, document that proof and narrow the gate accordingly rather than inventing a useless reader.

Do not clear this gate merely because no existing fixture happens to use a dynamic-type move.

## C. Other transient damage state

Audit every transient class currently represented by `transientStateObserved`.

For the supported ordinary subset, classify each relevant transient state as one of:

1. **required and observable** → implement authoritative observation;
2. **provably irrelevant to the supported subset** → document and test the proof;
3. **relevant but not safely observable yet** → retain a precise fail-closed limitation.

Do not replace a broad blocker with optimistic defaults.

Prefer narrowing the supported subset over building a giant generalized battle-state mirror.

# 3. Primary goal B — runtime calculator goldens against the official 2.0.5 ROM

C4b proved arithmetic against the host oracle.

C4c must compare DualDex output with **actual official-ROM battle outcomes**.

Extend the existing H&S runtime probe/scenario infrastructure rather than creating an unrelated one-off harness unless there is a compelling reason.

For every runtime fixture:

* begin from a documented legal save/state;
* use normal game/controller behavior where possible;
* record all operands needed to reproduce the calculation;
* record the actual HP delta / damage result from the game;
* record the corresponding DualDex predicted 16-roll range or exact applicable result;
* demonstrate that the observed ROM result is valid under that calculated range and mechanic state;
* where deterministically reproducible, prefer stronger equality/invariant assertions over screenshots or manual notes.

Runtime evidence must be machine-checkable where reasonably possible.

## Required runtime matrix

Build a bounded but meaningful set. Aim to runtime-prove at least:

1. **Neutral ordinary physical or special hit**

   * no unusual modifiers.

2. **STAB and/or non-neutral type effectiveness**

   * demonstrates the post-roll path is correct in the real ROM.

3. **Non-neutral stat stage**

   * exercise a real observed stage and raw battle stat path.

4. **Badge boost**

   * player-side eligible battle;
   * authoritative SaveBlock1 badge state;
   * demonstrate that the relevant badge boost actually affects the calculation.

5. **One additional modifier family**

   * crit, Rain/Sun, Reflect/Light Screen, or burn;
   * choose the scenario that can be made most deterministic and authoritative.

6. **Doubles target-count behavior**
   if the target-count reader is implemented in this slice:

   * two present targets → spread reduction;
   * one remaining present target → no spread reduction.

Do not fake state directly in RAM merely to obtain a passing runtime result.

If a modifier is prohibitively nondeterministic, use an upstream-supported legal setup or a repeatable runtime invariant. Document the limitation honestly.
