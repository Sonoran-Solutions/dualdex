# Quota-Aware Android Cloud Backup Design

Status: implementation candidate in progress (2026-10-12). The selector, filesystem inventory, and archive codec now have production sources, but the candidate `QuotaAwareBackupAgent` is not registered and staged review/import and per-file conflict handling are implemented but await device validation and owner acceptance. This is not a shipping or end-to-end backup claim.

## Problem and current contract

PR #185 (`13d215271df4b58138c708c972a74409289d6bb0`) is merged. The allowlist in [ANDROID_BACKUP_POLICY.md](ANDROID_BACKUP_POLICY.md), `backup_rules.xml`, and `data_extraction_rules.xml` deliberately includes canonical saves, legacy/fallback recovery data, and the exact legacy-assignment preference. It excludes ROM caches, ordinary preferences and secrets, debug output, staging, and unrelated files. Android 12+ already has separate cloud and device-transfer sections; Android 9–11 expresses the split with `clientSideEncryption` and `deviceToDeviceTransfer` require-flags. Preserve the complete current device-transfer set.

The Thor aggregate measured 118,773,282 bytes: essential battery saves and metadata 919,695; states/resume markers 9,512,064; thumbnails 17,153; recovery copies 108,324,370. The measured set is 4.53 times a 25 MiB quota. The source manifest is private and must remain outside the repository. While 919,695 bytes is comfortably below the proposed cloud payload limit, its aggregate alone does not prove that every ROM identity, valid canonical save, and required metadata record was enumerated. Thor selector coverage is therefore **NOT_RUN**; no individual-file simulation is claimed.

Android Auto Backup is best-effort and its cloud quota can vary by transport. XML paths have no wildcard support, so XML cannot pick `battery.sav` from arbitrary SHA-256 directory names. Android 12+ explicitly separates `<cloud-backup>` from `<device-transfer>`, allowing cloud exclusions while retaining local transfer. See the [Auto Backup guide](https://developer.android.com/identity/data/autobackup), [BackupAgent API](https://developer.android.com/reference/android/app/backup/BackupAgent), and [FullBackupDataOutput API](https://developer.android.com/reference/android/app/backup/FullBackupDataOutput).

## Architecture comparison

| Approach | Correctness and security | Complexity / migration | Device transfer and testability |
| --- | --- | --- | --- |
| A. Custom `BackupAgent` selects files directly | Can inspect transport flags and reported quota, enumerate dynamic ROM directories, and stream an allowlisted manifest. Must implement stable reads, restore staging, and all fail-closed checks. | Medium-high. Changes manifest wiring and replaces default selection behavior. Callback lifecycle is restricted; API 28–34 supports full backup and transport flags. Set `android:fullBackupOnly="true"` to keep file-based Auto Backup semantics. XML must not be treated as a second selector once the custom agent owns `onFullBackup()`. | Best separation: cloud path selects compact payload; D2D path submits the existing complete roots. Pure selector and archive codec can be host-tested; actual Android transport still needs disposable-device validation. `onQuotaExceeded()` reports an aborted operation and quota, it is not a retry hook. |
| B. Dedicated compact cloud snapshot | A versioned archive with an explicit manifest, hashes, and exact ROM SHA-256 destinations gives a bounded, inspectable unit. Atomic temp-build then rename means a partial archive is never eligible. A custom agent is still needed to choose this snapshot for cloud but bypass it for D2D. | Medium-high. Adds archive, integrity, stale-source, staging, and cleanup rules. Building on every save write adds disk churn; building only in the backup callback avoids that, but requires agent-controlled selection. | Preserves D2D when agent sends the existing full roots for that transport. Snapshot format and selector are straightforward to test without Android. Restore can stage the entire archive before offering import. |
| C. Separate XML policy only | Android 12+ can exclude state/recovery roots from cloud while retaining them for D2D, but paths cannot select dynamic `battery.sav` files inside `saves_v2/<sha256>/`. Including all of `saves_v2/` remains potentially over quota. ### Recommendation

Use a **custom file-based `BackupAgent` that constructs one temporary compact snapshot for cloud, and streams the unchanged PR #185 allowlist for device-to-device transfer**. This is A's transport dispatch with B's atomic snapshot as its cloud payload. Keep the selector/codec as pure Kotlin and separate from production save execution. Do not persist a continuously refreshed snapshot; build it during the backup callback from a stable captured file set, verify source stamps again before finalizing, write a completion marker only after hashes and manifest validate, then atomically rename the temporary archive. Delete stale temporary work on the next run. Never modify canonical or historical files.

The manifest should be a bounded versioned JSON or binary header followed by ZIP entries stored without compression (save data is already compact/unpredictable). Each entry records exact lowercase 64-hex ROM SHA-256, category, normalized archive-relative destination, byte size, and SHA-256 content digest. Bound entry count, manifest bytes, path length, total uncompressed bytes, and archive bytes. Reject unknown versions, duplicate destinations, duplicate metadata, unsafe paths, mismatched identity directories, bad hashes, and truncated archives. Never include ROM payloads, ordinary preferences, API keys, logs, or arbitrary files.

For cloud, use `FullBackupDataOutput.getQuota()` when available (API 26+) and a conservative maximum of 20 MiB or 80% of the reported quota, whichever is smaller, less a fixed 256 KiB container/manifest reserve. This leaves room below the documented nominal 25 MB quota and for transport accounting. If no trustworthy positive quota is available, use the 20 MiB cap. If the net payload allowance is non-positive, refuse. `onQuotaExceeded()` only reports that the operation was halted/rolled back; a later attempt can adapt to its reported quota. It must not mark protection successful.

## Deterministic backup priority and outcome

Inventory discovery must be independent of metadata validity. Walk each allowlisted save root and record every observed `.sav` and `.state`; derive canonical identities from valid 64-hex directory names under `saves_v2/` even when `metadata.json` is absent, malformed, or unreadable. A failed directory listing, permission error, malformed identity directory containing save files, or interrupted scan sets `inventoryComplete=false` and forces refusal. Metadata validates identity but never decides whether a save exists. For each discovered identity choose exactly one valid canonical `battery.sav`; only if it is absent/invalid may a recovery battery save with an explicit verified assignment substitute. Require the matching identity metadata in the same essential bundle. Every observed save must be selected, listed as excluded/unprotected with a reason, or listed under `unassignableSourcePaths`; no empty identity set or missing metadata can turn an incomplete inventory into success. Unknown legacy saves are unassignable, never guessed by filename/title.

`LegacySaveCatalog.getSourceKey()` hashes the lowercased absolute canonical file path, so the existing `assigned_*` preferences are not a portable assignment format across devices or Android user profiles. A cloud snapshot may include a legacy save only when its source device can verify the current assignment; encode a portable binding of archive-relative entry path + content SHA-256 + exact ROM SHA-256 + canonical destination filename in the snapshot manifest. Restore validates that binding against the staged entry and imports it under `saves_v2/<rom-sha256>/`; do not restore old absolute-path catalog keys as portable authority. If a legacy assignment is unavailable or fails the content/path check, classify the source as unassignable and refuse essential coverage rather than infer ownership.

1. **Tier 1, essential:** one current canonical battery save per known valid ROM identity plus identity metadata. A verified recovery save can cover an identity with no valid canonical file; preserve the source classification and hash.
2. **Tier 2, recovery:** verified legacy battery saves or additional recovery material not needed for Tier 1. Include only after all Tier 1 identities fit.
3. **Tier 3, convenience:** resume/quick/manual states, thumbnails, and further generations, after Tiers 1 and 2.

Selection is deterministic: validate a complete inventory, reject duplicate source records and any normalized source path claimed by different ROM identities, group essential files by full SHA-256, sort identities lexicographically, and test the complete essential set as one unit. A `saves_v2/<hash>/` state or thumbnail must declare that same hash; recovery and legacy entries require a verified assignment. If discovery is incomplete, a save is unassignable, any identity lacks an unambiguous essential save/metadata pair, or the full essential set exceeds the budget, return **REFUSAL**, select no payload, and report all identities that remain unprotected plus unassignable paths. Do not choose a newest global subset that silently leaves one ROM without its only save. If all essentials fit, include optional files in tier then identity then normalized-path order while each complete file fits; skip oversized optional records and continue to later candidates. Return SUCCESS only if all eligible records fit, PARTIAL if every essential is covered but optional records were excluded, and REFUSAL if complete essential coverage cannot be achieved. Report exact selected bytes, budget, inventory completeness, covered/unprotected identities, unassignable paths, and exclusion reasons. Never delete local history to fit.

The prototype in [QuotaBackupSelection.kt](../app/src/test/java/com/dualdex/emulator/QuotaBackupSelection.kt) implements the inventory, ownership, all-essential-or-refuse, and budget contracts over synthetic metadata only. Production archive construction must hash each source's bytes while selecting/copying and compare the copied digest, byte count, and captured mtime against the selected record. The serialized manifest is hashed exactly; the completion marker stores that manifest SHA-256 and a digest of the sorted `(entry path, content SHA-256)` set. Before emission, reread and validate the completed archive, manifest digest, marker binding, and every entry digest. A same-size/same-mtime content change, absent marker, mismatch, malformed manifest, or interrupted temp build makes the snapshot unusable. Only then atomically rename the archive into its backup-visible path.

## Restore contract

The agent must override API 28–34's `onRestoreFile(ParcelFileDescriptor, size, destination, type, mode, mtime)`: Android's default implementation writes directly to the supplied destination. Route the exact new archive path `cloud_backup/dualdex-snapshot-v1.zip` to a private pending-import file, never to canonical storage. Route ordinary allowlisted save-tree and legacy-catalog paths into restore-session staging as well; do not call the default writer for them before the restore set has been checked. Unknown paths are rejected. At `onRestoreFinished()`, validate archive bounds, format version, complete marker, every entry path, expected directory/hash relationship, file length and SHA-256, metadata identity, and the full set before exposing an import. Path traversal, links, duplicate destinations, malformed metadata, mismatched hashes, and truncation reject the staged set. Do not overwrite or delete a valid canonical save during backup preparation or restore validation.

After cloud snapshot validation, show a user-reviewed import list keyed by full ROM SHA-256 and title hint. A fresh install can retain staged saves before a ROM is configured; selecting the exact same ROM bytes resolves to that identity. Same title with different bytes stays separate; different titles with identical bytes use the same identity. Before import, compare the staged record with the current canonical save. If a newer valid local save exists, require explicit user choice and retain both until the choice is committed. Never silently replace newer valid data. Write accepted content through the existing save integrity/atomic transaction utilities into a new staging target, recheck digest, then commit atomically. Interrupted import leaves canonical files intact and pending content retryable.

For ordinary full-file restore paths (the existing PR #185 tree format), stage the complete file set and validate the paths before committing. Require explicit confirmation even with no collision, preserving the original destination for ordinary save files. Every existing destination requires explicit replacement and retention, regardless of timestamps or apparent validity. This also safely handles pre-agent cloud backups that contain ordinary save paths. API 28–34's restore callback has no transport flags, so old direct-path cloud data cannot be distinguished from a D2D file tree; path-based dispatch alone must not guess. Applying the same staging/conflict rule to both modes is an intentional restore safety change. The newer cloud archive has a distinct path and always goes through pending import.

Corrupt or unsupported archives are rejected without changing existing saves. Missing optional states are normal. Legacy content is imported only when its exact verified assignment metadata is present; otherwise present it as unassigned and do not associate it. Save states remain version-sensitive: verify compatibility with the current emulator core before offering load, and treat state rejection as non-destructive. Do not automatically restore or load an incompatible state.

## Android-version and transfer contract

| Encryption flag | D2D flag | Backup dispatch | Restore dispatch on API 28–34 |
| --- | --- | --- | --- |
| absent | absent | Refuse; emit no save payload. | Unknown format/path is rejected; no assumption about transport. |
| present | absent | Cloud: emit only the bounded `cloud_backup/dualdex-snapshot-v1.zip`. | Exact archive path is staged as pending cloud import. |
| absent | present | D2D: emit the complete PR #185 roots and legacy catalog without the cloud cap. | Ordinary save-tree entries are staged and validated, then offered for per-file confirmation; every existing destination requires an explicit replacement choice. |
| present | present | Treat D2D as the route because that flag identifies a local transfer; encryption is an independent property. Emit the complete D2D set, not the cloud snapshot. | Restore callback flags are unavailable on API 28–34. The archive path identifies new cloud format; ordinary save paths use the staged full-tree path above. |

The table applies to Android 9–11 (API 28–30) and 12+ (API 31–34); the policy differs only in the platform's XML configuration (`requireFlags` versus `<cloud-backup>` / `<device-transfer>`). `FullBackupDataOutput` transport flags are available from API 28 and quota from API 26. API 36.1 adds `FullRestoreDataInput` with restore transport flags, but it is outside this app's supported API range. For supported releases, restore routing uses the dedicated archive path and validated full-tree format, not an assumed restore transport. Keep `disableIfNoEncryptionCapabilities="true"` for Android 12+ cloud backup and do not rely on XML as a second selector after custom-agent ownership is configured.

If flags identify neither route, refuse and emit no save payload. No cross-platform/iOS transfer is in scope. Before rollout, verify custom-agent/XML behavior and both transports on API 28–30 and 31–34 disposable profiles. Existing XML and manifest are not changed in this spike.

## Failure handling and security assumptions

- Source files are private app data but can change while a game is running. Capture path/length/mtime/content SHA-256, open with no-follow semantics where available, copy to private temp files while hashing copied bytes, compare the copied digest with the selected digest, reread the source digest/stamp, and abort on any mismatch. A future implementation should coordinate only with a read-safe save snapshot boundary; do not hold the emulator save lock across slow transport I/O.
- The backup callback can run when the app UI and content providers are unavailable. The agent must use only direct file APIs and small pure Kotlin code; no activity, database/provider initialization, network call, user prompt, or app-level singleton.
- The archive is untrusted on restore. Enforce size/count limits before extraction, use allowlisted destinations, reject symlinks and traversal, and stage on the same filesystem for atomic commit.
- ROM identity is exact SHA-256; display names never establish ownership. No ROM bytes are enumerated or serialized.
- Do not claim protection until a successful backup is observed by the platform. Refusal/partial outcomes should be surfaced through safe diagnostic state without logging paths, hashes, save bytes, credentials, or game content.
- Cloud snapshot restore always remains staged for user-reviewed import. Ordinary full-tree restore paths require validation and per-file confirmation; every existing destination remains pending an explicit replacement choice. The API 28–34 callback cannot tell whether an old direct-path dataset came from cloud or D2D, so both legacy full-tree modes use the same conflict-safe commit contract.

## Validation plan and current results

Synthetic selector tests cover one/multiple ROMs; orphaned canonical saves; incomplete inventory; same-title/different-hash identity; large optional state and >100 MB recovery; missing canonical with verified recovery; unassigned legacy; cross-ROM recovery claims; misattributed states; duplicate/bad metadata; traversal and ROM-payload rejection; essential over-quota; exact-budget and one-byte-over; transport dispatch for all four flag combinations; restore path routing; budget reserve; portable assignment across changed app-data roots; stable input-order results; content changes preserving size/mtime; marker/manifest/content binding; and refusal when full coverage is impossible. The fixtures contain metadata only, not ROM or save contents.

The Thor aggregate implies the essential category total (919,695 bytes) is below 20 MiB, but the protected per-file manifest is not present in the repository and no individual-file coverage test was run. **Thor selector simulation: NOT_RUN.** Issue #12's latest comment records that safe same-signer update checks passed and cloud restore/D2D restore remain NOT_RUN on disposable profiles. This task does not repeat device operations.

Before implementation, validate archive construction/restore using synthetic files and injected interruption/mutation; run the selector tests; inspect APK manifest and rules; then run exact-head CI. Before enabling the feature, test actual cloud quota callbacks and cloud/D2D selection/restoration on disposable Android 9–11 and 12+ devices/profiles. Never test destructive restore using the owner's only save data.

2. Choose the user-visible location for incomplete/refused backup status; background callbacks cannot prompt directly.
3. Confirm whether a verified legacy save with no canonical file counts as essential coverage (recommended: yes, but label it recovery-derived).
4. Confirm whether a cloud backup refusal should retain the previous successful cloud version (platform rollback is documented on quota excess, but deliberate agent refusal needs transport validation).
5. Approve the 20 MiB/80%-of-reported-quota budget and archive reserve after measurements on supported transports.
6. ## Issue #186 implementation checkpoint (2026-10-12)

The selector has been promoted from test-only code into `app/src/main/java/com/dualdex/emulator/backup/QuotaBackupSelection.kt`. It now refuses explicit non-positive quotas, bounds per-entry size/count/path/manifest inputs, uses checked aggregate arithmetic, isolates full SHA-256 identities, and validates legacy bindings against only canonical `saves/` or `saves_fallback/` battery-save sources with nonempty content and a matching digest. `SaveBackupInventory` walks the three permitted save roots without following symlinks and reports incomplete/invalid inventory conditions. `CloudSnapshotArchive` writes deterministic stored ZIP entries with a bounded versioned binary manifest and completion marker, verifies content hashes and source stamps, validates before publication, and atomically moves the completed archive into its destination.

The unregistered candidate `QuotaAwareBackupAgent` now routes encrypted cloud versus D2D callbacks, emits the selected cloud archive, and explicitly walks and emits every regular D2D file under the three approved save roots plus the exact legacy catalog file. The shared `BackupFileTreePolicy` governs D2D emission and ordinary restore staging, rejects symlinks and incomplete traversal, and permits recovery copies, metadata, thumbnails, resume markers, and legacy migration files. The D2D sender preflights the complete inventory with the same admission check used by restore staging: nonempty files, at most 4 GiB per file, 16 GiB in total (including the catalog), 16,384 files, and a 1 MiB legacy catalog. Canonical `saves_v2/<hash>/metadata.json` (including nested metadata under that identity) is also capped at 1 MiB and validated by the same bounded JSON parser and case-insensitive ROM-hash comparison during sender preflight and staged restore validation. Malformed JSON, missing hashes, and mismatched identities refuse the transfer without modifying local saves. A rejected entry refuses the transfer before emission; sizes and metadata contents are rechecked immediately before each file is emitted. Nonempty `.tmp`, `.bak`, `.orig.bak`, and `.migrated.bak` files are retained for staged review under these bounds; empty copies refuse the transfer rather than being silently dropped. ROM payload extensions (`.gba`, `.agb`, `.gb`, `.gbc`, `.nds`, case insensitive), including temporary and recovery suffixes, are rejected in every save root by both sender and receiver. This extension check is defense in depth, not ROM content detection. Cloud archives remain capped at 20 MiB. The archive codec checks category-specific path and ROM ownership, metadata and essential-save relationships, and rechecks every source after the complete copy before publication. Host tests include actual emitted file inventory, oversized D2D recovery data, fully checksummed invalid ownership claims, and mutation of an earlier source while copying a later entry.

### Refusal and restore counting

All prohibited or incomplete full-backup operations throw `IOException` from the callback boundary and record `REFUSED_OR_INCOMPLETE`. This includes unsupported transport flags, empty/refused essential selection, missing source stamps, failed archive construction, and exceptions during emission. Success status is set only after emission returns. Normal callback completion concludes a full-backup pass; the API permits `IOException` ([BackupAgent reference](https://developer.android.com/reference/android/app/backup/BackupAgent#onFullBackup(android.app.backup.FullBackupDataOutput))). Auto Backup keeps the latest successful dataset ([backup location](https://developer.android.com/identity/data/autobackup#BackupLocation)). **A thrown exception is an application abort signal, not verified proof of preservation of the previous remote dataset.** On a disposable transport, first establish a usable backup, inject a refused/failed subsequent attempt, and verify that the earlier backup remains recoverable.

The receiver counts files separately using the same 16,384-file and byte limits as the sender. Valid zero-byte directory headers do not consume file admission or materialize empty staging directories; file callbacks create necessary parents. Directory callbacks have a separate bounded counter allowing up to `16,384 × floor(4096 / 2) + 2` headers, derived from the maximum number of shortest ancestor segments for every admitted file plus the catalog/cloud roots. Duplicate directory headers are harmless within that limit; duplicate file destinations fail. Headers retain path, type, size and symlink checks. Host regressions exercise 16,384 files interleaved with parent headers and the independent directory boundary. Actual Android transport emission of directory callbacks remains **NOT_RUN** and must be verified before activation.

### Staged restore review and import

`StagedRestoreStore` validates each complete restore set and atomically publishes a `restore_staging/ready-<UUID>` directory. Incomplete callbacks and rejected sets remain isolated. Review works after process restart and without a ROM loaded. The Saves screen exposes **Review restored saves**, with paginated file choices showing the full ROM hash, title hint, source/destination, size, available date, and local conflict. Cloud format v1 has no file timestamps; its dates are shown as unavailable. Closing or cancelling keeps both sets unchanged.

Every import requires confirmation. An existing destination, including older or empty files, requires **Replace and retain local**. Size, modification time, and SHA-256 are captured at review and rechecked before copying and immediately before commit; same-size/same-time mutations invalidate the review. Source archives are revalidated and checked again after extraction and at the commit boundary. A missing destination that appears after review cannot be silently overwritten. Same-title games remain separated by full ROM hash.

Imports hold `SaveStateManager.globalSaveLock` and the existing core coordinator lock. They refuse to run while any game is loaded or emulation is running; close the game in Settings first. A verified temporary copy is fsynced on the destination filesystem. Any displaced local file is copied and verified into a unique, durably published `ready-local-<UUID>` session before atomic replacement. Existing `.bak` files are never rotated by this workflow. Unsupported atomic moves or failed retention abort; there is no non-atomic fallback. A successful rename followed by a failed directory sync reports that the file was imported with durability unconfirmed. Interrupted work leaves the original staged backup and any retained local copy available; a retry must review current files. Atomicity is per file, not an all-or-nothing multi-file transaction. No automatic cleanup deletes pending or retained copies; retention uses additional private storage and insufficient space refuses the import.

A restored battery or state raises the local resume barrier to at least the latest existing state timestamp and the restored timestamp. Each newly generated live state receives an ordering timestamp greater than that barrier, the battery, and all existing states, assigned before fsync and publication. Only successful native state writes use this rule; import does not stamp restored states as fresh. It keeps old future-dated slots blocked while allowing newly played auto-resume and manual states to resume immediately, including after a process restart or clock rollback. These ordering timestamps may be ahead of wall-clock time when old data was future-dated; the barrier is never lowered to admit an old state. Manual battery import validates the candidate byte size and captures a reliable live SRAM backup, then publishes and parent-directory-syncs the monotonic barrier before loading the candidate into the core or committing the canonical battery. A marker copy or directory-sync failure aborts import before live SRAM changes and leaves the canonical battery and old resume bytes unchanged, including when no prior barrier exists. The old auto-resume file is removed only after the guarded battery commit succeeds. The shared copy helper reports success only after syncing the renamed target's parent directory; a failed post-rename sync may leave the marker present but never permits the battery commit. Standalone clear-auto-resume uses the same barrier publisher. This preserves state bytes while preventing automatic state loading from rolling back a reviewed battery import. A failed attempt may conservatively raise this barrier before the final save rename; it never deletes a state. Imported states are only offered through the existing manual state-load flow and its size/native compatibility checks. The import UI does not claim core compatibility without the matching ROM.

Verified cloud legacy bindings map only to their validated ROM hash and canonical battery destination. Ordinary D2D legacy files retain their original recovery paths and remain unassigned for the existing migration UI. Restored absolute-path legacy catalogs and resume markers are retained as reference records, not installed as local authority. Recovery and temporary files remain staged even after import; normal save handling may clean up canonical temporary paths later.

`StagedRestoreStoreTest` covers session publication/restart, invalid sets, cloud extraction and verified legacy binding, source/local mutations, all local timestamp orderings, explicit retention and recovery, write/retention/move interruption, symlinks, resume barriers, loaded-game refusal, and concurrent stale imports with synthetic bytes. These host checks do not establish Android transport, filesystem durability, dialog behavior, or emulator state compatibility on a device.

The candidate agent remains unregistered. Instrumented API 28–34 UI/lifecycle and storage checks, disposable cloud/D2D transport tests, and owner acceptance of these policies remain activation blockers. Keep PR #188 draft and unmerged, and issues #186 and #12 open.
